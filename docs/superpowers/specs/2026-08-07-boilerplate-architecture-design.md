# Pink Paprikaa — Boilerplate Architecture (Phase 0)

**Date:** 2026-08-07
**Status:** Approved
**Scope:** Foundation only — workspace, tooling, configuration, CI/CD, and empty-but-wired apps and packages.
**Explicitly out of scope:** design system components, visual design, content migration, page building. Those land in Phases 1–6.
**Companion:** [product requirements](./2026-08-07-pink-paprikaa-site-redesign-design.md) — that document owns _what_ the site must do; this one owns _how_ it is built. See [`docs/README.md`](../../README.md) for how their phase numbering reconciles.

---

## 1. Purpose

Replace five hand-written, fully duplicated static HTML pages with an Nx monorepo housing two Next.js applications and a real design system — without taking the live site down at any point.

The current site has three structural problems this foundation is built to prevent recurring:

| Problem today                                                                                                   | Prevented by                                                                                 |
| --------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 43 MB of raw PNGs (25 files, 1.2–2.2 MB each) served unoptimised                                                | Build-time image pipeline + Lighthouse CI byte-weight budget that fails the PR               |
| Header, nav, footer and scripts copy-pasted across 5 files                                                      | Design system package with lint-enforced import boundaries                                   |
| No structured data, `sitemap.xml` referencing a page that does not exist, `robots.txt` outside the build output | `packages/seo` with typed JSON-LD builders; sitemap and robots generated by the app at build |

**Success criteria for Phase 0:** `pnpm install && pnpm verify` passes from a clean clone; every gate in §12 runs green in CI; the live site is untouched.

## 2. Decisions locked

| Area                   | Decision                                                                                       |
| ---------------------- | ---------------------------------------------------------------------------------------------- |
| Repository             | **New workspace, created fresh** at `pink-paprikaa-web/`. The existing repo is left untouched. |
| Monorepo               | Nx 23 (matches the globally installed v23.1.1), pnpm workspaces                                |
| Framework              | Next.js 16, App Router, `output: 'export'` (fully static)                                      |
| Applications           | `web` (marketing) + `blog` — two separate Next.js apps                                         |
| Hosting                | Netlify, three sites (web, blog, storybook); artifacts built in CI, not by Netlify             |
| Design system          | Style Dictionary → Tailwind v4 `@theme` → tailwind-variants; Radix for behaviour               |
| Component architecture | Atomic — atoms / molecules / organisms / templates in the DS; pages owned by apps              |
| Content                | Git-based. Content Collections (MDX) for the blog; Zod-validated typed data for site content   |
| Quality gates          | Vitest + Testing Library, Playwright, axe-core, Lighthouse CI budgets — all PR-blocking        |
| Commits                | Conventional Commits via commitlint, authored through Commitizen, enforced by husky            |
| Rendering              | No server, no runtime cost. Recurring hosting spend: **₹0/month**                              |

### Rejected alternatives

| Rejected                            | Reason                                                                                                                                                               |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Gatsby** (for the blog)           | Maintenance-only since Netlify's Feb 2023 acquisition; core team dispersed; plugin ecosystem largely abandoned. Its DX is reproduced in §9 without the dead runtime. |
| **Turborepo**                       | Genuinely lighter, but Nx's generators, project graph and module-boundary enforcement were wanted deliberately.                                                      |
| **Vercel**                          | Hobby tier forbids commercial use; a restaurant site needs Pro at about $20/mo (≈₹1,700/mo) for no benefit a static export can't already get.                        |
| **Panda CSS / Vanilla Extract**     | Both excellent, but Tailwind v4's `@theme` is already a token engine. The gap was a token _source of truth_ above Tailwind (§8), not a different CSS engine.         |
| **Contentlayer**                    | Unmaintained since Stackbit's acquisition.                                                                                                                           |
| **Netlify Image CDN**               | Would work, but couples image handling to the host and doesn't run in Storybook or local dev.                                                                        |
| **Single app with a `/blog` route** | Simplest option and was offered; separate apps chosen for independent deploy cadence.                                                                                |
| **Building in the existing repo**   | Originally planned, then reversed: a fresh workspace avoids legacy files, keeps 43 MB of PNG history out of the new repo, and removes all risk to the live site.     |

## 3. Repository strategy and cutover

A **new workspace is created from scratch**, in a sibling directory. The existing `pink-paprikaa-site` repository is left entirely untouched.

|           |                                                                                        |
| --------- | -------------------------------------------------------------------------------------- |
| Location  | `/Users/rishavpandey/Professional Works/pink-paprikaa-web/`                            |
| npm scope | `@pink-paprikaa-web/*`                                                                 |
| Old repo  | Untouched. Keeps deploying the live site; serves as the content reference for Phase 2. |

```bash
npx create-nx-workspace@latest pink-paprikaa-web \
  --preset=apps \
  --workspaceType=integrated \
  --workspaces \
  --packageManager=pnpm \
  --formatter=prettier \
  --nxCloud=skip \
  --defaultBase=main \
  --aiAgents=claude \
  --interactive=false
```

`--preset=apps` produces an empty integrated monorepo — no sample application to delete. `--workspaces` enables pnpm workspaces, `--nxCloud=skip` holds to the decision in §5, and `--aiAgents=claude` wires Nx's Claude Code integration at creation.

**Why a fresh workspace rather than building in place:**

- No legacy files to work around, and no Nx configuration contending with the existing Tailwind CLI setup
- The 43 MB of PNGs in the old repo's history stay in the old repo — the new one starts small and stays small
- The live site carries zero risk for the entire build, because nothing touches its repository

**Git.** `create-nx-workspace` initialises a local repository. No remote is configured initially. The remote is pointed at GitHub at cutover — either a new repository or the existing `pink-paprikaa-site` remote — decided in Phase 6.

**Cutover (Phase 6).** Point Netlify at the new repository, change the build command and publish directory, verify, then archive the old repository. Rollback is repointing Netlify at the old repo, which remains fully deployable throughout.

**Branching.** `dev` as the integration branch, `main` protected and deploying to production — same model as today.

## 4. Workspace layout

```
pink-paprikaa-web/
├── apps/
│   ├── web/                  Next.js · App Router · output:'export' → pinkpaprikaa.com
│   ├── web-e2e/              Playwright
│   ├── blog/                 Next.js · basePath:'/blog' → proxied onto apex domain
│   └── blog-e2e/             Playwright
├── packages/
│   ├── design-tokens/        DTCG token source → Style Dictionary → theme.css + tokens.ts
│   ├── ui/                   Atomic components + Storybook
│   ├── content/              Zod schemas + typed site content
│   ├── seo/                  JSON-LD builders (schema-dts) + Metadata helpers
│   └── utils/                Framework-agnostic helpers
├── tools/
│   ├── eslint-config/        Flat-config presets
│   ├── typescript-config/    base / next / react-lib / node
│   └── image-pipeline/       sharp → AVIF + WebP ladder + LQIP
├── assets-src/               Image originals — never deployed
├── docs/superpowers/specs/
├── .husky/
├── .github/workflows/
├── nx.json
├── pnpm-workspace.yaml
├── commitlint.config.ts
└── package.json
```

Packages are imported by npm scope — `@pink-paprikaa-web/ui`, `@pink-paprikaa-web/design-tokens` — never by relative paths crossing a package boundary.

### Why the blog is a subdirectory, not a subdomain

`blog.pinkpaprikaa.com` would split domain authority across two hostnames. Instead the blog app sets `basePath: '/blog'`, deploys as its own Netlify site, and is proxied onto the apex domain:

```
/blog/*  https://pp-blog.netlify.app/blog/:splat  200
```

A `200` rewrite (not a `301`) means the URL stays `pinkpaprikaa.com/blog/...`. One domain for SEO, two fully independent deploys.

The existing Petpooja redirects move into `apps/web/public/_redirects` so they survive the export, and are unchanged:

```
https://order.pinkpaprikaa.com/*   https://pinkpaprikaa.petpooja.site/:splat   301!
https://pickup.pinkpaprikaa.com/*  https://pinkpaprikaa.petpooja.com/menu/:splat  301!
```

## 5. Nx configuration

**Inferred tasks (Project Crystal).** Nx plugins derive targets from the tool configs that already exist — `next.config.ts`, `vite.config.ts`, `eslint.config.mjs`, `playwright.config.ts`. No `project.json` files are written by hand. Caching inputs and outputs are inferred from the same configs, so cache correctness follows tool config automatically.

**Plugins:** `@nx/next`, `@nx/react`, `@nx/js`, `@nx/eslint`, `@nx/vite`, `@nx/playwright`, `@nx/storybook`.

**Module boundaries** — enforced by `@nx/enforce-module-boundaries`, not convention:

| Project                          | Tags                           |
| -------------------------------- | ------------------------------ |
| `apps/web`                       | `type:app`, `scope:web`        |
| `apps/blog`                      | `type:app`, `scope:blog`       |
| `apps/*-e2e`                     | `type:e2e`, matching scope     |
| `packages/ui`                    | `type:ui`, `scope:shared`      |
| `packages/design-tokens`         | `type:tokens`, `scope:shared`  |
| `packages/content`               | `type:content`, `scope:shared` |
| `packages/seo`, `packages/utils` | `type:util`, `scope:shared`    |
| `tools/*`                        | `type:tool`, `scope:shared`    |

| Tag            | May depend on                                         |
| -------------- | ----------------------------------------------------- |
| `type:app`     | `type:ui`, `type:content`, `type:util`, `type:tokens` |
| `type:ui`      | `type:ui`, `type:util`, `type:tokens`                 |
| `type:content` | `type:util`                                           |
| `type:util`    | `type:util`                                           |
| `type:tokens`  | _(nothing)_                                           |
| `scope:web`    | `scope:web`, `scope:shared`                           |
| `scope:blog`   | `scope:blog`, `scope:shared`                          |
| `scope:shared` | `scope:shared`                                        |

Two consequences worth stating explicitly: the design system can never import application code, and `web` and `blog` can never import each other. Both are lint errors, not review comments.

**Nx Cloud: off.** Local computation cache is sufficient for a single developer. Remote caching gets enabled only if CI wall-time becomes a real problem — no reason to send workspace metadata to a third party for no current benefit.

## 7. Linting, formatting, hooks and commits

### ESLint

ESLint 10, flat config, composed in `tools/eslint-config`:

- `typescript-eslint` — `strictTypeChecked` + `stylisticTypeChecked`
- `eslint-plugin-react`, `eslint-plugin-react-hooks`
- `eslint-plugin-jsx-a11y`
- `@next/eslint-plugin-next`
- `@nx/eslint-plugin` — module boundaries
- `eslint-plugin-perfectionist` — deterministic import and object-key ordering
- `eslint-plugin-tailwindcss` — Tailwind v4 aware
- `eslint-config-prettier` — last, disables all formatting rules

**Two project-specific rules:**

1. **No raw hex.** Literal colour values are banned in `className` and JSX. Everything routes through design tokens. This is the rule that stops `#EE2C68` being retyped by hand and slowly drifting.
2. **Atomic layering.** Nx boundaries operate per project, so layering _inside_ `packages/ui` is enforced with `no-restricted-imports` zones: an atom cannot import a molecule, a molecule cannot import an organism, and so on upward only.

### Prettier

Prettier 3 with the existing project settings preserved — `printWidth: 100`, double quotes, 2-space indent — plus `prettier-plugin-tailwindcss` for class sorting, configured with `tailwindStylesheet` pointing at the design system's CSS entry (Tailwind v4 requires this; the old `tailwindConfig` option does not apply).

### Git hooks (husky 9)

Split so that `pre-commit` stays under roughly five seconds. A slow pre-commit hook is a hook that gets bypassed.

| Hook         | Runs                                                           | Purpose                                           |
| ------------ | -------------------------------------------------------------- | ------------------------------------------------- |
| `pre-commit` | `lint-staged` → Prettier + `eslint --fix` on staged files only | Fast, formats what you touched                    |
| `commit-msg` | `commitlint`                                                   | Rejects non-conventional messages                 |
| `pre-push`   | `nx affected -t typecheck lint test build`                     | The real gate, before anything leaves the machine |

### Commits

Conventional Commits via `@commitlint/config-conventional`, authored through Commitizen using **`@commitlint/cz-commitlint`** — the prompt is generated from the same config `commitlint` enforces, so the two can never disagree. Run with `pnpm commit`.

Scopes are constrained to the workspace projects: `web`, `blog`, `ui`, `tokens`, `content`, `seo`, `utils`, `tools`, `ci`, `deps`.

### Root scripts

Defined once in the root `package.json` so local and CI invocations cannot drift apart:

| Script              | Runs                                              | Called by                                      |
| ------------------- | ------------------------------------------------- | ---------------------------------------------- |
| `pnpm verify`       | `nx affected -t typecheck lint test build`        | `pre-push` hook, CI, and §1's success criteria |
| `pnpm verify:all`   | `nx run-many -t typecheck lint test build`        | Full-workspace check, release prep             |
| `pnpm commit`       | `cz` (Commitizen via `@commitlint/cz-commitlint`) | Authoring every commit                         |
| `pnpm format`       | `nx format:write`                                 | Local                                          |
| `pnpm format:check` | `nx format:check`                                 | CI                                             |

`pnpm verify` is the single name for "everything that gates a change". The pre-push hook and the CI job both call it, so a green local run means a green CI run — there is no second list to keep in sync.

## 8. Design system

### Token pipeline

Tokens are authored **once**, in W3C DTCG format, in `packages/design-tokens/tokens/`. Style Dictionary builds them into every consumable form:

```
tokens/*.json  →  Style Dictionary  →  dist/theme.css   (Tailwind v4 @theme block)
                                    →  dist/tokens.ts   (typed constants)
                                    →  dist/tokens.json (Storybook catalogue)
```

Nothing hand-writes a Tailwind theme. Apps and Storybook import the generated `theme.css`; any JavaScript that needs a token value imports from `tokens.ts`. One source, three outputs, no drift.

### Three token tiers

| Tier      | Example                                     | Purpose                                                     |
| --------- | ------------------------------------------- | ----------------------------------------------------------- |
| Primitive | `pink.500` = `#EE2C68`                      | Raw palette. Never referenced by a component.               |
| Semantic  | `color.brand.primary` → `pink.500`          | What a colour _means_. This is what components use.         |
| Component | `button.bg.default` → `color.brand.primary` | Per-component overrides where a component needs to diverge. |

This tiering is what makes retheming a bounded change rather than a find-and-replace, and it is the practical difference between a design system and a components folder.

### Atomic layers

```
packages/ui/src/
  atoms/       Button  Text  Icon  Badge  Input  Spinner  Divider
  molecules/   Card  FormField  NavItem  PriceTag
  organisms/   Header  Footer  MenuSection  Gallery  ContactBlock
  templates/   PageShell  ArticleLayout  MenuLayout
  .storybook/
```

**Pages are not in the design system.** Templates accept content as props; apps own the routes that bind real data to them. This keeps the DS free of content and routing concerns, and the boundary is lint-enforced (§5, §7).

### Component authoring

- **tailwind-variants** for variant APIs — chosen over CVA specifically for **slots**, which multi-part organisms (a `Card` with root / header / body / footer) genuinely need, plus built-in `tailwind-merge` so consumer overrides resolve correctly instead of producing duplicate conflicting classes.
- **Radix UI** for interactive behaviour — dialog/lightbox, drawer, tabs, accordion, navigation menu. Focus trapping, ARIA wiring and keyboard handling are where accessibility bugs actually live; this is not the place to hand-roll.
- **Storybook 10** lives inside `packages/ui`, builds static, deploys as its own Netlify site. `@storybook/addon-a11y` runs axe in the panel during development.

Phase 0 ships the pipeline, the Storybook shell, and exactly one reference component (`Button`) proving the token → variant → story → test path end to end. Real components arrive in Phase 1 once designs are supplied.

## 9. Content architecture

The Gatsby developer experience, reproduced without Gatsby:

| Gatsby concept              | Replacement                                                                                |
| --------------------------- | ------------------------------------------------------------------------------------------ |
| GraphQL data layer          | **Content Collections** — Zod schema per collection, fully typed output, no query language |
| `gatsby-node` `createPages` | `generateStaticParams()` reading the collection                                            |
| Page templates              | `template` field in frontmatter selects a layout component from `packages/ui/templates`    |
| MDX shortcodes              | MDX `components` map → design system components                                            |
| `gatsby-image`              | `tools/image-pipeline` + the DS `<Picture>` component (§10)                                |

Structured site content — menu categories and items, offers, gallery, FAQs, opening hours, location — lives in `packages/content` as Zod-validated typed data rather than MDX. It is queried like data, not rendered like prose, so a schema serves it better than a document format. The Zod schemas double as the input to the JSON-LD builders in §11, so structured data cannot drift from displayed content.

## 10. Image pipeline

Static export disables `next/image` optimisation (`images.unoptimized: true`), which makes this infrastructure rather than an enhancement — and it is the single highest-impact item in the whole rebuild.

`tools/image-pipeline` runs sharp at build time:

- Originals read from `assets-src/`, which is never deployed
- Emits **AVIF + WebP + fallback** across a fixed width ladder
- Generates LQIP blur placeholders inlined as base64
- Content-hashed filenames for immutable caching
- Manifest of dimensions consumed by the DS `<Picture>` component, which emits a proper `<picture>` with `<source srcset>` and explicit `width`/`height` so nothing shifts on load

Build-time rather than Netlify Image CDN: host-agnostic, deterministic, identical output in Storybook, local dev and production, no vendor coupling. It costs build time and buys portability.

The Lighthouse byte-weight budget (§12) is what stops the 43 MB problem from ever returning — a regression fails the PR rather than being discovered in production.

## 11. SEO package

`packages/seo` provides, typed with `schema-dts`:

- JSON-LD builders — `Restaurant`, `LocalBusiness`, `Menu`, `BreadcrumbList`, `FAQPage`, `Article`
- Next.js Metadata API helpers — canonical URLs, Open Graph, Twitter cards
- Sitemap and robots generation

Builders take `packages/content` types as input, so structured data is generated from the same source that renders the page and cannot drift from it.

Each app generates its own `sitemap.xml` via `app/sitemap.ts` at build; the `web` app additionally serves a **sitemap index** referencing both. This fixes three existing defects: `robots.txt` and `sitemap.xml` currently sit outside the build output entirely, `sitemap.xml` lists an `offers.html` that does not exist, and no page has any structured data at all.

## 13. Deliberate version constraints

Standing rule: **no versions are hand-written into `package.json`.** Everything installs through `pnpm add`, resolving latest stable. The two exceptions below are deliberate, and each carries a removal criterion.

### TypeScript pinned to 6.x — not 7

`typescript@latest` is **7.0.2**, the Go-native compiler. `typescript-eslint@8.66.0` declares `typescript: >=4.8.4 <6.1.0`, and its `canary` (8.66.1-alpha.9) declares the same — no release or prerelease supports TypeScript 7.

Every type-aware ESLint rule runs through typescript-eslint. On TypeScript 7 they silently do not run. TypeScript **6.0.3** is the newest stable version the lint stack supports, and 6.x is actively maintained in parallel with 7, not a legacy branch.

> **Remove when:** typescript-eslint publishes a stable release whose `typescript` peer range admits `^7`.

### `eslint-plugin-jsx-a11y` peer override

ESLint latest is **10.8.0**. `eslint-plugin-jsx-a11y@6.10.2` still declares `eslint: ^9`. This is stale metadata rather than a real incompatibility — the plugin does not use the ESLint APIs that changed in 10. Resolved with a single scoped entry:

```yaml
pnpm:
  peerDependencyRules:
    allowedVersions:
      "eslint-plugin-jsx-a11y>eslint": "10"
```

ESLint 9 was rejected because it already sits on the `maintenance` dist-tag; starting a new codebase on a winding-down line to satisfy one plugin's unpatched metadata is the worse trade.

> **Remove when:** jsx-a11y publishes a release declaring ESLint 10 support.

## 14. CI/CD

GitHub Actions. Netlify does **not** build — artifacts are built in CI so the Nx cache actually applies, then pushed with `netlify deploy`.

| Job          | Trigger        | Runs                                                   |
| ------------ | -------------- | ------------------------------------------------------ |
| `verify`     | every PR       | `nx affected -t typecheck lint test build`             |
| `e2e`        | every PR       | `nx affected -t e2e` (Playwright + axe)                |
| `lighthouse` | every PR       | Build `web`, serve, `lhci autorun` against §12 budgets |
| `deploy`     | push to `main` | Build all, `netlify deploy --prod` to three sites      |

`pnpm install --frozen-lockfile` everywhere. Node and pnpm versions come from `.nvmrc` and the `packageManager` field so CI and local can never diverge.

`main` is protected: PR required, all four jobs green.

## 17. Known costs

Stated plainly rather than discovered later.

1. **Maintenance surface.** Two Next.js apps, Storybook, and four CI gates is substantial for one maintainer working mornings and evenings. This was an informed choice — the simpler single-app option was offered and declined — but the cost is real.
2. **Build time.** The sharp image pipeline and Style Dictionary codegen both add to cold builds. Nx caching makes warm builds cheap; cold CI builds will be slower than the current Tailwind-only setup.
3. **Two TypeScript majors behind `latest`** until typescript-eslint catches up (§13).
4. **Two repositories in play until Phase 6.** The old repo keeps the live site and the 43 MB of PNG history; the new one stays clean. The tradeoff is that content porting in Phase 2 reads across two directories, and both must be kept straight until the old one is archived.

## 18. Traps hit during setup

Each of these cost real time and none is obvious from documentation. Recorded so they are not rediscovered.

| Trap                                                                                                                                                                         | Resolution                                                                                                                          |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| **Nx 23's interactive prompt only offers `--template`** (GitHub template repos — `nrwl/react-template` is React + Express). The classic `--preset` list is gone from the UI. | Pass `--preset=apps` explicitly and skip interactive mode. It maps internally to `nrwl/empty-template`.                             |
| **pnpm 10 blocks dependency build scripts by default.** Nx's native bindings were left uncompiled with only a warning.                                                       | Declare `onlyBuiltDependencies` in `pnpm-workspace.yaml` — committed config survives a fresh clone; `pnpm approve-builds` does not. |
| **Nx's generated `ci.yml` runs `npm ci`** in a pnpm workspace and calls Nx Cloud commands (`start-ci-run`, `record`, `fix-ci`).                                              | Replaced entirely. Would have failed on the first push.                                                                             |
| **`nx format:check` fails on `pnpm-lock.yaml`.**                                                                                                                             | Added to `.prettierignore`. Machine-generated; formatting it fights pnpm on every install.                                          |
| **Nx's default `.prettierrc` uses single quotes**, contradicting the established project style.                                                                              | Replaced with printWidth 100 / double quotes / `trailingComma: es5`.                                                                |
| **`--aiAgents=claude` generates configs for every agent**, not just Claude — `.codex/`, `.cursor/`, `.gemini/`, `.opencode/`, `AGENTS.md` (byte-identical to `CLAUDE.md`).   | Removed the unused ones. Kept `.agents/skills/` and `.github/skills/`, which hold the Nx skills.                                    |
| **Prettier turns `~$20 (~₹1,700)` into `~~$20 (~~₹1,700)`** — valid GFM strikethrough, so the text renders struck through.                                                   | Avoid `~` as an "approximately" sign in Markdown. Use "about" or `≈`.                                                               |

**The general lesson:** `create-nx-workspace` output is a starting point, not a finished configuration. Verify every generated file against this spec rather than assuming the generator agrees with it — on this workspace, four of its defaults did not.
